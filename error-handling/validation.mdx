The `Validation<T>` interface is a `@FunctionalInterface` with a single abstract method, `validate(T value)`, that throws `ValidationException` when the supplied value does not satisfy an expected condition. Because it is a functional interface, any conforming lambda expression can be assigned to a `Validation<T>` variable — no concrete class is required. `BankServiceImpl` uses this pattern to define four focused, single-responsibility validators as private instance fields, keeping input-checking logic inline and easy to read.

## The Validation Interface

```java
package util;

import exceptions.ValidationException;

@FunctionalInterface
public interface Validation<T> {
    void validate(T value) throws ValidationException;
}
```

The interface is intentionally minimal: it carries no default methods and imposes no state. The sole contract is that `validate` either completes normally (input is acceptable) or throws `ValidationException` (input is not). This design means validators can be passed, stored, and called uniformly regardless of the type `T` they inspect.

## Validators in BankServiceImpl

`BankServiceImpl` declares four validators as `private final` instance fields using lambda expressions. Each validator is scoped to a single check and throws a fixed, user-readable message on failure.

```java
private final Validation<String> validateName = name -> {
    if (name == null || name.isBlank()) throw new ValidationException("Name is required.");
};

private final Validation<String> validateEmail = email -> {
    if (email == null || !email.contains("@")) throw new ValidationException("Please enter correct email");
};

private final Validation<String> validateType = type -> {
    if (type == null || !(type.equalsIgnoreCase("SAVINGS") || !type.equalsIgnoreCase("WITHDRAW")))
        throw new ValidationException("Type must be SAVINGS or CURRENT");
};

private final Validation<Double> validateAmountPositive = amount -> {
    if (amount == null || amount < 0)
        throw new ValidationException("Please enter a valid amount");
};
```

**How each validator is used:**

- **`validateName`** — called at the start of `openAccount()`. Rejects a name that is `null` or consists entirely of whitespace.
- **`validateEmail`** — called at the start of `openAccount()`. Rejects an email that is `null` or does not contain the `@` character.
- **`validateType`** — called at the start of `openAccount()`. See the warning below about its actual runtime behavior.
- **`validateAmountPositive`** — called at the start of `deposit()`, `withdraw()`, and `transfer()`. Rejects a `null` amount or any value below zero.

All four validators execute before any repository access, ensuring that malformed input never reaches the data layer.

<Warning>
  **`validateType` contains a logic error in the source code.** The condition as written is:

  ```java
  if (type == null || !(type.equalsIgnoreCase("SAVINGS") || !type.equalsIgnoreCase("WITHDRAW")))
  ```

  The second operand of the inner `||` is `!type.equalsIgnoreCase("WITHDRAW")`. This is `true` for any string that is not `"WITHDRAW"` — which includes `"SAVINGS"`, `"CURRENT"`, and virtually every other value. Because of short-circuit evaluation, the `||` is almost always `true`, making the whole condition `!(true)` = `false`, so the exception is **almost never thrown**. In practice, `validateType` only rejects `null` and the exact string `"WITHDRAW"` (case-insensitive). The intended behavior — rejecting everything except `"SAVINGS"` and `"CURRENT"` — is not what the code implements. A correct condition would be:

  ```java
  if (type == null || !(type.equalsIgnoreCase("SAVINGS") || type.equalsIgnoreCase("CURRENT")))
  ```

  The documentation above reflects what the source code **actually does**, not what was intended.
</Warning>

## Writing Custom Validators

Because `Validation<T>` is a `@FunctionalInterface`, you can implement additional validators using the same lambda pattern without modifying any existing class:

```java
Validation<String> validatePhone = phone -> {
    if (phone == null || !phone.matches("\\d{10}"))
        throw new ValidationException("Phone must be 10 digits.");
};
// Usage:
validatePhone.validate("5551234567"); // passes
validatePhone.validate("abc");         // throws ValidationException
```

The lambda must accept a single parameter of type `T` and either return normally or throw `ValidationException` — that is the complete contract.

## Validation Summary

| Validator | Input type | Condition that throws | Exception message |
|---|---|---|---|
| `validateName` | `String` | `name == null \|\| name.isBlank()` | `"Name is required."` |
| `validateEmail` | `String` | `email == null \|\| !email.contains("@")` | `"Please enter correct email"` |
| `validateType` | `String` | `type == null \|\| type.equalsIgnoreCase("WITHDRAW")` (effective behavior — see warning above) | `"Type must be SAVINGS or CURRENT"` |
| `validateAmountPositive` | `Double` | `amount == null \|\| amount < 0` | `"Please enter a valid amount"` |

<Tip>
  Because `Validation<T>` is a `@FunctionalInterface`, you can assign any lambda that accepts a `T` and throws `ValidationException`. This makes it straightforward to introduce new validators — such as phone number format, minimum deposit amount, or password strength — without modifying any existing class.
</Tip>

<Note>
  Validators are called at the top of each `BankServiceImpl` method before any repository access, so invalid input is rejected before any data is read or written. This means a failed validation will never leave the repository in a partially-modified state.
</Note>
